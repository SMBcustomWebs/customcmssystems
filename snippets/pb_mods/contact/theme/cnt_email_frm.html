The token is cleared so the send below is skipped - a link pointing at a row that was never created is worse than no mail at all, because the person clicks it and is told their link did not work. ================================================ THE CONFIRMATION MAIL - THIS IS THE BOT CHECK. Nothing on this form asks the visitor to prove they are a person. Instead the address has to prove itself: the row is written 'pending' and one mail goes to the address. Opening the link in it is what promotes the row (confirm-subscription.php). A bot does not read the mailbox. A typo does not reach a real one. Both rows stay pending forever, and no send loop touches a pending row. This is why there is no captcha here. A captcha guesses whether the visitor is a person BEFORE letting the address through, costs every real person a puzzle, and puts Google's script on whatever page this tile happens to sit on. This waits for proof instead and costs one click. SENT WHEN THE ROW IS NEW OR STILL PENDING. Pending means the last mail went unread or unnoticed, and re-sending it is the useful thing to do - it reuses the SAME token, so an older link still works. An address already 'subscribed' gets nothing: they are on the list and a second mail is just noise. from IS K_EMAIL_FROM, the address this domain's SPF record authorizes. reply_to is K_EMAIL_TO so an answer reaches a person rather than bouncing off a no-reply. FIELD NAMES ARE BARE. COUCH ADDS THE frm_ PREFIX. tags.php:5636 publishes every submitted field as frm_ + the field's name. So name="email" is what makes work. These were name="frm_email" until 2026-09-19, which made Couch publish frm_frm_email. THE HONEYPOT INPUT. OFF-SCREEN, NOT display:none AND NOT hidden. Bots have skipped display:none and type=hidden inputs for years; a field that is in the layout, focusable in principle and merely positioned outside the viewport still reads as real to them. INVISIBLE TO ASSISTIVE TECH TOO. aria-hidden keeps a screen reader from announcing it and tabindex=-1 keeps it out of the tab order, so nobody using the page any way at all can fill it by accident. It has a label because a bot checks for one. autocomplete=off so a browser never helpfully fills it in and locks a real person out of the form. The inline style is deliberate. This element must be invisible even if assets/css/user.php is stale or has not been uploaded - a visible honeypot is a field real people fill.
THE SUBMIT MARKER. Read at the top of this file as cnt_sent. Its only job is to be present in POST when this form is the one that was sent, because k_success alone cannot tell. THERE WAS A PER-IP THROTTLE HERE AND IT HAD TO COME OUT. addons/data-bound-form/throttle.php refuses a submission when the same IP created ANY page recently - throttle.php:80 has no template filter, so it counts every row in K_TBL_PAGES. That is not a near-miss, it is the common case. Saving a tile in the admin inserts a page row stamped with the author's IP (edit-page-builder.php:196), so the first test submission after an edit was always refused. On the live site a customer who places an order - also a page row - and then uses a sign-up inside the window gets refused the same way. It also leaked its own field name into the error list, because tags.php:5599 labels each error with the field's label or, when there is none, its name: "cnt_throttle: ...". WHAT STILL GUARDS THIS FORM. The honeypot above stops commodity bots, and the confirmation mail means nothing reaches the list without somebody opening a mailbox. The only thing the throttle added was a cap on how fast this site could be made to SEND confirmations. If that ever matters, the control belongs on the thing being protected - a count of subscriber rows created in the last few minutes, which no order or tile save can inflate - not on a shared page-creation counter. NO CAPTCHA HERE, AND THAT IS NOW A DECISION RATHER THAN AN OMISSION. reCAPTCHA is loaded in kfunctions.php and its keys are in config.php, so it is still one cms:input away. Three reasons it is not used on this tile: 1. IT WOULD NOT ADD ANYTHING THE CONFIRMATION MAIL DOES NOT. Nothing reaches the list without somebody opening a mailbox, so a captcha would stop a submission that is already harmless by the time it lands. 2. IT COSTS EVERY REAL PERSON A CLICK. Not a puzzle - v2 checkbox goes green on one click for most people, and only shows the picture grid when Google's score is uncertain. But on a form whose whole appeal is that it asks for ONE thing, one extra control is still a real proportional cost. cnt_basic_frm.html makes the opposite call for exactly this reason: three fields already, so the same click barely registers. 3. IT PUTS GOOGLE ON SOMEBODY ELSE'S PAGE. This is a PageBuilder tile - it can sit on any page of the site. Adding the widget would load a third-party script wherever an author drops it, on a site built to avoid exactly that, and the notice would have to disclose Google as users/register.php does. register.php is the opposite case and keeps its reCAPTCHA: it is one known page, the form is long enough that a checkbox is noise beside it, and an account is worth more to an attacker than a list row.
